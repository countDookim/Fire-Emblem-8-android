# Project brief: native Kotlin Android reimplementation of Fire Emblem 8 (GBA)

Owner's brief (2026-10-24) condensed, with all later amendments merged in (owner request 2026-10-30: concise docs).
The verbatim original is in git history (`git show dcf7da2:docs/PROJECT_BRIEF.md`). New amendments go in the table
at the end and win over the text above it.

## Inputs
- Decomp (the spec): [fireemblem8u](https://github.com/FireEmblemUniverse/fireemblem8u) pinned at
  `reference/DECOMP_VERSION` (not StanHash/fe8: mostly asm; docs/decisions/0007).
- Code repo `countDookim/Fire-Emblem-8-android`, ROM repo `countDookim/Fire-Emblem-8-rom` (ROM + all ROM-derived
  data, mGBA harness, reference data; published as releases by its `publish-assets` workflow). Both private; attach
  both with push access via the GitHub app. Never ask the owner for passwords or tokens. Default branch `master`.

## Goal
A native Kotlin Android app that is a **1:1 copy** of the game (behaviour bit-exact vs the original), designed like a
modern moddable game: not an emulator, no line-for-line transliteration, no GBA memory-layout mimicry. The ROM
supplies assets and is the test ground truth. Modding = **extension points only** (data/VFS, event hooks, strategy
interfaces); the app ships no non-original features: no touch gameplay, QoL flags, alternate formulas or widescreen
(docs/decisions/0009). The only touch input shipped: an on-screen GBA button overlay (D-pad, A, B, L, R, Start,
Select) sending exactly GBA keys.

## Hard requirements
1. **Architecture:** by game system; idiomatic Kotlin (sealed states, enums, data classes); Compose for menus and
   settings only, game view on OpenGL ES 3.0. Code style: Google's Android Kotlin style guide (new/changed code).
2. **Low-end phones:** zero per-frame allocations in game loop and renderer; hot data in primitive arrays behind
   typed wrappers; GPU rendering at 240×160 scaled by shader; fixed ~59.73 Hz logic decoupled from display;
   low-latency `AudioTrack`; minSdk 26; allocation tests + JVM frame-time benchmark in CI.
3. **Docs:** KDoc on every public declaration (what, why, non-obvious choices); ported functions cite their source
   (`/** Ported from src/battle_main.c: BattleMainCB2 */`); a README per module; `ARCHITECTURE.md`, `MODDING.md`
   (kept current), `docs/decisions/` (short ADRs); Dokka site.
4. **Progress bar** at the top of README (`Progress: ████░░ 41% (1234 / 3010 functions)`, labelled an estimate) +
   per-system table, computed by `tools/progress.py` (in-scope decomp functions ported AND covered by a passing
   test), regenerated by CI. Out-of-scope code (link-cable `sio_*`, debug menus) is shown separately and left out of
   the percentage; a function with a retail caller stays in scope (ROADMAP). Never inflate it.
5. **Reuse by future FE6/FE7 ports:** game-neutral `gbafe.*` (engine, shared systems, formats `gbafe.<table>` with a
   `game` field, tools) vs FE8-only `fe8.*`; per-game differences only via data, strategies or per-game extractor
   packages; CI enforces `gbafe` never uses `fe8` (0010). Game-neutral GBA library `:gba:*` (0012); Kotlin
   Multiplatform, targets jvm + android only (0013).

## Modding groundwork (designed in, not retrofitted)
- **Input:** abstract actions, never raw buttons in game logic; buttons/touch/controllers interchangeable; UI
  elements expose screen bounds + actions for hit-testing.
- **Feature flags:** anything non-original behind flags; vanilla stays bit-exact (the product ships none).
- **Data:** all game data in versioned, schema-validated JSON, compiled to primitive arrays at load; none hardcoded.
- **Maps:** Tiled `.tmj` (layout, collision, warps, events, units, connections) + PNG tilesets, converted from decomp.
- **Event scripts:** readable text format, allocation-free interpreter, new logic without recompiling (ADR 0001).
- **Graphics:** PNG + JSON metadata; replacement/hi-res texture packs via the override layer; vanilla palettes.
- **Audio:** MIDI + voicegroup definitions, WAV/OGG effects, all overridable.
- **Text:** localization files with readable tags (`{PLAYER}`, `{PAUSE 30}`); Unicode font system.
- **Mechanics:** formulas/AI as strategy interfaces with vanilla impls (alternatives only in tests); battle rolls via
  `BattleRolls` (switching 2-RN to 1-RN hit is one method). Typed, allocation-free event bus.
- **Flags/variables:** registry named after decomp constants; mods can add more.
- **Saves:** versioned, migratable, per-mod sections; import original `.sav`.
- **Mod loader:** folders/zips with manifest (id, version, deps, order); layered VFS overrides any path; hot reload
  in debug builds.
- **Camera** not tied to 240×160 (vanilla stays 240×160); seedable central RNG (vanilla exact) + game clock.
- **Debug menu** (debug builds only): warp, flags/vars, items, battles, inspect state.

## ROM and distribution
- Never commit the ROM or anything extracted from it to the code repo (`.gitignore`); ROM-derived data lives only in
  the ROM repo and its releases.
- **Public release builds ship no game content:** the player imports their `.gba` (SHA1-checked) on first launch,
  extracted on device into the VFS `base` layer from a committed offsets manifest; ROM not kept; CI checks the APK
  (0011, M4-03..05).
- **No APK bundles game data, debug/test builds included** (owner 2026-11-08, replaces the 2026-10-28 amendment):
  every build needs a ROM imported on the device.

## Environment
Scheduled runs (a Claude Cowork task) and owner-PC sessions (Claude Code in the owner's WSL2 Ubuntu) + GitHub
Actions. Never Android Studio, an emulator or computer use.
- **CI** on every push: debug APK, full tests (unit, differential, allocation, frame time), progress bar,
  `docs/port_map.json`, Dokka; uploads APK + summary; rolling `latest` release with the APK; cached Gradle/SDK.
- **Scheduled runs** never install the Android SDK: JDK, kotlinc, Gradle wrapper (JVM targets only) and a local
  retrying Maven mirror (0005). The owner's PC has the SDK (`~/android-sdk`) and may build `:app`.
  `tools/setup.sh` is minimal, idempotent, fast (< 3 min, logs its duration) and fetches the ROM repo's release
  assets (ROM, headless mGBA, reference data, extracted assets).
- Game logic stays Android-free (pure Kotlin/JVM, tested in seconds); Android code in the thin `:app` module.
- Decomp reference data (function list, symbols) generated once by `tools/gen_reference.py` and committed.
- **Verification** (capture-first, ROADMAP): a capture (CAP row, in the ROM repo) comes before the port; an INV test
  fixes which functions a capture window runs; a PORT writes only those. Differential tests vs headless mGBA with
  identical inputs, comparing state and frames (software renderer path on the JVM). A function counts as ported
  only with a `Ported from` KDoc and a passing
  `@VerifiesPort` test against ground truth (0006).
- **Manual testing (owner's phone):** installs from `latest`; keep `docs/MANUAL_TEST.md` (what is newly testable and
  how) current. Owner files GitHub issues labelled `user-report`: top priority; reference them in the fix commit;
  close only when a test verifies the fix, or ask the owner to confirm.

## Resume files (small and current)
- `HANDOFF.md` (one screen): NEEDS USER at the top when blocked, last CI result, branch, **Next task** (ID, files,
  first command, done criteria), known bugs.
- `docs/TASKS.md`: open rows only, by lane, with IDs, kind (CAP / INV / PORT / WIRE), acceptance, deps, status.
- `docs/plans/ROADMAP.md`: milestones, task rules, owner decisions. `docs/plans/UNVERIFIED.md`: generated list of
  written-but-unverified code (`tools/unverified.py`).
- `docs/port_map.json` (generated by `tools/progress.py`), `docs/MANUAL_TEST.md`.

## Schedule
Scheduled task every 6 h (`CRON_TZ=Asia/Jerusalem 50 0,6,12,18 * * *`; owner 2026-11-04). Each run is a fresh session, **~30 min** from
its own start (a little over is fine to finish a nearly done task). Every run:
1. Clone; run `tools/setup.sh` (it records the start via `tools/run_clock.sh start`).
2. Read only `HANDOFF.md`, open `user-report` issues and the last CI result if it failed (not this brief unless
   HANDOFF says something changed).
3. Priority: failing CI → `user-report` issues → HANDOFF's Next task (no re-planning) → the first `todo` row in
   `docs/TASKS.md` whose deps are done, in either lane; claim it first and skip rows claimed by another run
   (CLAUDE.md rule 10). If a `wip/` branch is newer than HANDOFF, the last run was interrupted: continue it first.
   If a lane has fewer than 5 open rows, break the next ROADMAP milestone into rows.
4. Commit + push after every completed step; unfinished work on `wip/<task-id>`; never leave `master` broken.
5. Work until ~minute 23, **never end early** (when a task finishes, start the next, on `wip/` if needed). Then by
   ~30: local tests, `MANUAL_TEST.md` if something became testable, precise Next task in
   HANDOFF, commit, push. Don't wait for CI.
6. Usage limit hit: the run just stops; never work around limits or reschedule.
7. Blocked (permission, setup, unclear or irreversible decision): write it under NEEDS USER in HANDOFF, open a
   `needs-user` issue, continue with something else.

Be honest: flag uncertainty, never claim untested behaviour works, say clearly when blocked.

## Milestones
1. Toolchain, CI, skeleton, docs, ADRs. 2. Extraction into moddable formats. 3. Rendering (GPU + offscreen), input,
audio, override layer. 4. Boot to title verified vs mGBA; first manual-test APK. 5. Core loop, saves, flag registry,
script interpreter. 6. Remaining systems, each with strategy interfaces and event hooks, as M6-A…M6-J
(opening wired, player phase, map combat, enemy phase, Prologue completable, info screens, battle animation,
chapters 1–4 systems, prep screen and world map, late game), each ending in a device-testable result
([ROADMAP](plans/ROADMAP.md)). 7. Mod loader, debug menu (debug builds), on-screen GBA buttons. Milestones 1–5 are done.
