# 0002 — Data: versioned JSON + JSON Schema, compiled to primitive tables

**Context.** All game data (items, classes, characters, terrain, shops, AI tables, chapter data...) must
be moddable, schema-validated, versioned JSON, yet runtime access must be allocation-free and fast.

**Decision.**
- Each table is `data/<table>.json` in the VFS:
  `{ "format": "fe8.items", "version": 1, "entries": [ { "id": "IRON_SWORD", ... } ] }`.
  Ids are the decomp's constant names (`ITEM_SWORD_IRON` → `"IRON_SWORD"` mapping is generated and
  documented); numeric indices are assigned at compile time and never written by hand.
- `schemas/<table>.schema.json` (JSON Schema 2020-12) is the public contract for modders/editors. Tests
  validate every shipped data file against its schema (test-only validator dependency).
- Loading: kotlinx.serialization (strict, unknown keys rejected) → DTOs → `TableCompiler` packs columns
  into primitive arrays (`IntArray`, `ByteArray`, bitsets). Game code uses typed wrappers
  (`items.might(item: ItemId)`, `ItemId` is a value class over `Int`). DTOs are discarded after load.
- Mods override whole files by path (0003) or patch them with `data/<table>.merge.json` (RFC 7386 JSON
  Merge Patch on `entries` keyed by `id`), applied in mod load order; new ids get new indices after
  vanilla ones, so vanilla indices stay stable.
- `version` bumps require a migration function in the loader for older mod files.

**Consequences.** Vanilla JSON is generated by the extractor (milestone 2) into the ROM repo — never
committed here. Schema files *are* committed (they are not ROM-derived). Slight load-time cost; zero
run-time cost.
